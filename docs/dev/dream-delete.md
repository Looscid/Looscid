# Dream delete spec

Status: proposal, not a description of shipped behavior.

Code baseline: main at `1332eb0752af66af0273ee7d4a96c262b395f51f` (`1332eb0`). Source references refer to that pinned commit, not future main, except section 4.1, which explicitly uses the later pinned main HEAD. Function names are used where an exact declaration line was not pinned. This commit adds documentation only; it does not implement deletion.

## 1. Existing behavior

- `docs/dev/cherry-upgrade.md` uses a lower-case, hyphenated spec filename, a plain heading, a proposal status, numbered sections and open questions. `docs/dev/FILES.md` requires accessibility markup to be copied verbatim. This spec follows that style; there was no delete spec in `docs/dev/` at the baseline.
- `DreamOptionsMenu` has no Delete item (`app/js/core.js:935-999`). Its shared button label is built as `More, Dream by <name>`. `DreamExtra` is an inline disclosure with heading focus, not a confirmation dialog (`app/js/core.js:616-638`). `ReplyItem` has a separate `Reply options` menu with Reply, Hear reply, Copy text, Share reply and profile actions, but no Delete (`app/js/core.js:1093-1125`).
- `useSavedDreams` calls `lcSyncOwnDreams` (`app/js/core.js:366-390`). The latter detects removed own Dreams with `d.user === ME`, filters them from saved Dreams and writes `LC_DREAMS_KEY`, `looscid_dreams` (`app/js/core.js:244-245,370-385`). It calls `lcNostr.hide(s.nid)` for removed saved entries with a Nostr id (`app/js/core.js:374`). This persistence path exists; the Delete UI does not.
- `hide(nid)` only records a valid event id in the device's hidden list (`app/js/nostr.js:775`). `HIDDEN_KEY` is `looscid_nostr_hidden` (`app/js/nostr.js:19`); `fetchOwn` uses hidden ids to avoid loading them again (`app/js/nostr.js:781-788`). Hide does not publish a NIP-09 kind-5 event. The export has hide but no relay-deletion API (`app/js/nostr.js:890-898`); hide does not delete relay copies.
- Draft deletion is real: `DraftsPage.remove` calls `deleteDraftItem` and refreshes its items (`app/js/create.js:205-207`); its Delete button calls `remove(draft.id)` (`app/js/create.js:222-223`). `deleteDraftItem` filters saved drafts by draft id and writes `DRAFTS_KEY` (`app/js/create.js:7-9`). `DRAFTS_KEY` is imported into `app/js/create.js`; its declaration and `getDrafts` / `saveDraftItem` are in `app/js/core.js`, with key `looscid_drafts`. Mirror this explicit action-to-removal pattern, but require confirmation for Dreams.
- In `app/js/circles.js`, `GroupAdminModal` renders pending Dreams through `pendingPosts.map`; the Approve and Reject buttons have style/className but no `onClick` handlers. They are not an existing deletion or moderation implementation to reuse. This citation names the function rather than guessing individual button line numbers.

## 2. Scope and Carter's decided behavior

- Offer deletion only for the author's own Dream: require `d.user === ME` both when building the menu and again when confirming. Never expose or execute it on someone else's content. Hiding, muting, blocking and rejecting another person's content are different actions.
- Carter decided: deleting an own root replaces its content with a minimal tombstone/placeholder whose exact visible text is `this Dream was deleted`. Replies stay readable and are NOT swept, including own descendants. Keep their parent/thread relationships so the placeholder gives the thread a head. This tombstone behavior is proposed, not existing code.
- Carter decided: no undo. The confirmation dialog is the safety step; a published kind-5 deletion request cannot be reliably recalled. Do not offer an undo promise or an undo timer.
- Carter decided: clean alerts and thread subscriptions pointing at the deleted Dream. Do not reopen these choices as questions. Deleting one reply must not unsubscribe or delete its surviving parent thread.
- An own reply can be deleted separately, but `ReplyItem` and the saved reply store need explicit wiring. Replies carry `isReply`, `replyTo` and optionally `replyToReply`; context resolves the immediate parent separately (`app/js/core.js:252-327`). Remove only the selected own reply, notify through `lcRepliesChanged`, and preserve descendants and siblings. `lcSyncOwnDreams` alone does not delete a reply held outside `looscid_dreams`.
- The subscription menu uses `dream._root || dream.replyTo || dream.id` (`app/js/core.js:969-974`). Resolve actual root/immediate-parent context before cleanup, especially for nested replies. A reply's deletion is not a deletion of the root or permission to publish deletion events for anyone else's replies. Removing local text/media references does not erase an independently hosted media file.

## 3. Proposed screen-reader-first UI

- Add visible `Delete` to the own-Dream `DreamOptionsMenu`, exact accessible label `Delete Dream`. For an own reply, add visible `Delete` to its existing menu with exact accessible label `Delete reply`; preserve the `Reply options` trigger label. Both paths use the same confirmation/removal controller.
- Selecting Delete closes the menu and opens a CONFIRMATION DIALOG before any state, storage or relay mutation. Use a labelled modal `alertdialog`, `aria-modal="true"`, a title referenced by `aria-labelledby`, and explanatory text referenced by `aria-describedby`. Do not repurpose the inline `DreamExtra` disclosure as a modal.
- Root title: `Delete this Dream?`. Root description: `Confirming replaces this Dream with a deleted-Dream placeholder on this device. Replies stay readable. Deletion cannot be undone. If published, deletion of its Nostr events will be requested, but relays may keep copies. Cancel makes no changes.` Reply title: `Delete this reply?`. Reply description: `Confirming removes this reply from this device. Other replies stay readable. Deletion cannot be undone. If published, deletion of its Nostr events will be requested, but relays may keep copies. Cancel makes no changes.`
- Move focus into the dialog, initially to Cancel. Trap Tab and Shift+Tab and keep the background out of the modal focus order. Confirm: visible `Delete`, exact accessible label `Delete Dream` or `Delete reply`. Cancel: visible `Cancel`, exact accessible label `Cancel Dream deletion` or `Cancel reply deletion`.
- Only the dialog's Delete action proceeds. Recheck ownership and selected id, prevent double confirmation while pending, and capture event metadata before removal. Cancel, Escape and any supported dismiss action make no changes and return focus to the captured More button, or the original Reply options trigger for a reply, not the disappeared menu item.
- On root success, focus the tombstone's programmatically focusable text. On reply success, focus the next surviving reply, the previous one if needed, or the view heading. Never focus a removed card's More button. Use the existing announcement mechanism: `Dream deleted from this device. Replies remain readable.` or `Reply deleted from this device.` Announce `Relay deletion requested. Relays may keep copies.` only when publication has actually been requested; on failure say `Relay deletion could not be requested. Copies may remain.` Do not announce global erasure as fact.

## 4. Proposed local persistence and linked traces

Use exact Dream/event ids and explicit linkage, not matching text, timestamps or an author's name. Preserve unrelated records. Existing helpers may swallow storage errors; verify durable writes before announcing success. All cleanup below is proposed, not an existing Delete transaction.

- `looscid_dreams` (`LC_DREAMS_KEY`, `app/js/core.js:244-245,366-390`): reuse `useSavedDreams` / `lcSyncOwnDreams` to remove the selected own root's original content. Extend the saved-Dream schema/read path to persist a minimal tombstone in this same store, retaining only identity, thread linkage and deletion marker, not original text/media. Current sync does not implement tombstones. Remove stale copies from mounted lists and ensure reload retains the placeholder, not the content. Do not silently invent an existing tombstone helper or key.
- `looscid_nostr_hidden` (`HIDDEN_KEY`, `app/js/nostr.js:19,775-788`): continue hide for each known event id of the selected item, including a selected reply. This is a retained suppression record, not a key to erase.
- `looscid_replies` (`LC_REPLIES_KEY`, `app/js/core.js:252-327`): filter only a selected own reply by id and call `lcRepliesChanged`. Root deletion preserves all replies and their `replyTo` / `replyToReply` relationships; no cascading sweep.
- `looscid_drafts` (`DRAFTS_KEY`, `app/js/core.js`, declaration and `getDrafts` / `saveDraftItem`; removal `app/js/create.js:7-9`): remove a saved draft only if explicitly linked to the deleted item. Existing draft-id filtering is not a published-Dream-to-draft mapping. Do not clear all drafts or guess a link.
- `looscid_reply_drafts` (`LC_REPLY_DRAFTS_KEY`, `app/js/create.js:383-389`; composer recovery/autosave at `app/js/create.js:481-524`): composer keys replies and quotes as `r:<parent.id>` and `q:<parent.id>`. Remove drafts directly targeting the deleted item with `lcReplyDraftSet(key, "")`; drafts targeting surviving replies remain. Unrelated New Dream autosave is not a linked trace to erase.
- `looscid_thread_subs` (`LC_THREAD_SUBS_KEY`, `app/js/core.js:5038-5055`): records contain `root`, `nid`, `label`, `since`. Clean subscriptions targeting the deleted root via `lcThreadUnsub(root)`, matching known root/event ids. For a selected reply, remove only subscriptions actually targeting that deleted item; keep subscriptions to the surviving parent root.
- `looscid_alerts` (`LC_ALERTS_KEY`, `app/js/core.js:4981-4982,5005-5033`): clean alerts explicitly pointing at the deleted item through `thread`, `ref` or `nid`, using `lcAlertsSave` and preserving its `looscid:alerts` dispatch. These fields are optional (`app/js/core.js:5025-5027,5054,5119`). Alerts about surviving replies must not be swept merely because they share the root; use item-specific linkage when available. Unlinkable previews are not safe identifiers.
- `looscid_inbox_seen` (literal key, `app/js/core.js:5063-5071,5110-5120`): shared deduplication ids for followed threads and inbox fetching. Clean linked visible alerts, but retain relevant seen ids as suppression tombstones so old notifications cannot replay. These functions do not establish a separate persisted inbox-content key.
- `looscid_liked` (`LC_LIKED_KEY`, `app/js/core.js:396-453`): remove the selected item's saved snapshot via the liked-store removal path; otherwise `lcLikedDreams` can revive it. `looscid_untagged` (`LC_UNTAGGED_KEY`, `app/js/core.js:454-468`): remove only a matching selected-item id if present.
- `looscid_redreams` (`LC_REDREAMS_KEY`, `app/js/core.js:474`; `lcRedreamsRaw` / `lcRedreamSet` at `app/js/core.js:475-482`): remove only the selected item's saved Redream snapshot and preserve the existing change notification.
- `looscid_feed_pins` (`LC_PINS_KEY`, `app/js/core.js:4784`; `lcPins` / `lcPinAdd` / `lcPinRemove` at `app/js/core.js:4790-4818`): records contain `kind`, `ref`, `label`. Remove a deleted root's `kind: "thread"` pin; retain unrelated people/feed pins and a deleted reply's surviving parent-thread pin.
- `looscid_pinned_dreams`, `looscid_muted_threads`, `looscid_not_interested` (declarations `app/js/core.js:884`, helpers `app/js/core.js:885-900`): remove the selected item's profile pin and not-interested id if present. Retain matching mute suppression while replies remain; never unmute a surviving root because one reply was deleted.
- `looscid_dream_edits` (`LC_EDITS_KEY`, `app/js/core.js:904`; `lcEdits` / `lcEditSave` / `lcWithEdit` at `app/js/core.js:905-918`): capture version/event metadata first, then remove only the selected item's stored edit history so it cannot restore deleted content.
- `looscid_nostr_queue` (`QUEUE_KEY`, `app/js/nostr.js:19`): cancel a queued creation only when positively linked to the deleted item, preventing republishing; never clear the whole queue. Audit and extend queue integration before implementation, keeping retryable deletion requests distinct from creation requests. Hide does not supply this cleanup.

Capture identity/linkage before mutation. Make confirmed removal, tombstone persistence, linked cleanup, hide and relay requests idempotent. A second activation must not delete another item. Minimal suppression and tombstone records are deliberate retained traces, not retained Dream content.

### 4.1 Deleted-Dream Alerts

This addendum is grounded in main HEAD `704d51912ce51a2893ce2115422744781753143a` (`704d519`). The following existing behavior was read in `app/js/core.js` and `app/js/alerts.js`; the deleted-Dream behavior below is a proposal, not shipped code.

- Existing types: `LC_ALERT_TYPES` in `app/js/core.js` contains `newDream`, `mention`, `reply`, `like`, `redream`, `quote`, `follow` and `system`, not a deletion type. `lcAlertPrefs` merges type defaults from `LC_ALERT_PREF_DEF` with `looscid_alert_prefs`. `LC_INBOX_TABS` / `lcAlertCats` (`app/js/core.js:1363-1365`) separately define Inbox filters; New Dreams and From Looscid currently appear only in All and Unread. `alertsView` / `lcCatList` in `app/js/alerts.js` use that category list and saved order/hidden settings, not the alert-type set alone.
- Existing storage and grouping: `lcNotify` / `lcAlertsSave` in `app/js/core.js` save alerts in local `looscid_alerts` (at most 100), dispatch `looscid:alerts`, and apply type preferences, audience, thread-mute, block and preview-word checks. With grouping enabled, `lcNotify` groups by equal type, unread state, a 30-minute window and equal `!!sub`; it does not group by Dream id or dedupe recipients. A grouped update increments count but does not accumulate target refs. `alertWhat` / `alertLabel` in `app/js/alerts.js` use type metadata, names, preview, time and unread state for spoken row labels. `notifRow` currently marks read on primary activation; only reply/mention/quote get its Reply action, and it does not provide tombstone navigation.
- Existing thread delivery: `lcThreadSub` in `app/js/core.js` saves `root`, `nid`, `label`, `since` locally; it is not a relay-published subscriber roster. `lcThreadAlert` uses type `reply` with `sub: true` and `thread`. `lcThreadCheck` excludes the active pubkey's own replies and shares event-id deduplication in `looscid_inbox_seen` with `lcInboxCheck`. `lcThreadWatch` schedules startup checks after 1.5 seconds and every 2 minutes, only while the app is visible; those checks fetch replies/inbox events, not deleted-Dream notices. The Replies filter's `Only threads I follow` checkbox in `alertsView` tests `n.sub`.

Carter decided: when a Dream is deleted, Dreamors who interacted with that Dream should get an Alert that a Dream they interacted with was deleted. Implement the following, separately from the existing reply/like/redream/quote/mention paths:

- Proposed type and filters: add the distinct type/key `deletedDream`, labelled `Deleted Dreams`, to `LC_ALERT_TYPES` and `LC_ALERT_PREF_DEF`, with an explicit enabled default and optional sound using the existing alert preference infrastructure. Add `deletedDream` to `LC_INBOX_TABS` / `lcAlertCats` so it is reachable under Inbox/Alerts All, Unread and a dedicated Deleted Dreams filter and the existing filter order/visibility settings. Do not disguise it as `system` or `reply`. Preserve user opt-outs and applicable mute/block controls; eligibility is not permission to bypass preferences. No decorative emoji or new sound-only status.
- Proposed recipients: only Dreamors with verified interaction with the exact deleted Dream: liked, replied, redreamed, quoted, or subscribed to its thread. Neither merely viewing it, following its author, being mentioned, nor interacting with a different Dream qualifies. Exclude the deleted Dream's author by stable account/pubkey identity, never display name. Union these interaction categories and dedupe by recipient identity plus original Dream/event identity, so one person gets one notice even after multiple interactions, edits, repeated checks or duplicate relay deletion events. Capture minimal interaction evidence before liked/redream/subscription cleanup; retain only identity/linkage needed for eligibility, not deleted content. Past interaction must not be inferred from an absent record: durable interaction evidence needs implementing where current snapshots cannot prove it. A private local subscription can qualify its own client; it cannot enumerate subscribers on other devices.
- Proposed notice and announcement: exact single-notice copy `A Dream you interacted with was deleted.` Use the same sentence with `announce` / `#looscid-live` when a genuinely new notice is durably saved, without moving focus or repeating it on redraw/read toggles. For root deletion the supporting text is `Replies remain readable.` Do not prefix the notice with an actor name via `alertWhat`, quote deleted text/media in a preview, promise global erasure, or use decorative emoji. Preserve `notifRow` / `alertLabel` unread/time labels, keyboard actions and focus restoration; add only the new notice semantics and navigation. Do not offer Reply to the deleted item.
- Proposed grouping: retain the existing type + unread + 30-minute-window grouping preference, but dedupe before grouping so retries or multiple interactions do not increment count. Use `deletedDream` with `sub` false/absent even if eligibility came from a subscription; never feed it to `lcThreadAlert`. It must not merge with subscribed-reply groups or use their `new replies in threads you follow` wording, name-based `T.by` wording, or the Replies-only subscription filter. A group of different deleted Dreams says `{count} Dreams you interacted with were deleted.` Extend grouped records to retain each unique tombstone target and make each reachable; count deleted Dreams, not interactions or repeated signals. Do not retain only the last target or rely on the current grouped update's unchanged `ref`.
- Proposed cleanup and tombstone link: resolve/store the original root identity and persist its minimal `this Dream was deleted` tombstone before saving the new notice. Use a tombstone-resolving target, not a dead id or the kind-5 event id as the content destination. Add an accessible `Open deleted Dream` action for a single notice; for groups, `Open deleted Dreams` exposes labelled individual tombstone targets. Opening the root preserves readable replies and focuses its tombstone; reload must retain the link. The cleanup above removes superseded interaction alerts/subscriptions, not this replacement deletion notice or its durable dedupe marker. Keep delivery event ids separate from content targets. Deleting a reply must not falsely tombstone its surviving root; resolve the deleted reply's retained context separately as in sections 2 and 7.
- Proposed delivery and limitations: alert creation remains local in each recipient's `looscid_alerts`; the author's `lcNotify` cannot write another Dreamor's storage. Extend the visible startup/every-2-minutes checks to detect authenticated deletion signals for previously interacted-with Dream ids, not only currently subscribed threads or inbox events addressed to the recipient. For published Dreams this needs relay-carried evidence, using the proposed signed NIP-09 kind-5 event in section 5 and verifying its signer owns the referenced original; it is not a purely local cross-client broadcast, nor an existing deletion fetcher. Each recipient client evaluates its own verified interaction evidence, records durable per-recipient/per-Dream deduplication distinct from reply-event deduplication, creates the tombstone and then calls the new local notification path. Polling, history retention and eligibility evidence require implementation; do not claim the current client can discover every historical interaction. A notice reaches a recipient only when their client runs and obtains the signal; closed/hidden/offline clients, unavailable relays or missing history can delay or prevent it. A local-only unpublished deletion has no relay signal and cannot notify other devices. No server push or guaranteed instant/global delivery is promised.

Acceptance checks for this addendum: each eligible non-author gets one notice across interaction categories and repeated/edit-version signals; non-interactors and the author get none. Test disabled preferences, mute/block handling, missing history, cleanup order and private subscriptions. Test All/Unread/Deleted Dreams and saved filter settings, grouping on/off, read state and time boundaries, separation from subscribed-reply groups, and access to every grouped tombstone after reload. Verify exact copy, announcement once without focus theft, keyboard/screen-reader navigation, preserved readable replies, and delayed visible-client delivery/offline retries without duplicates.

## 5. Proposed relay deletion

- Add a real NIP-09 publisher to `app/js/nostr.js`, separate from hide. Gather the selected item's original `nid` and known earlier edit/version event ids. Request deletion only for events whose author pubkey matches the active signing identity; `d.user === ME` is necessary for UI eligibility but not relay ownership proof.
- Sign a kind-5 event through the existing authorized Nostr signing flow, using current `created_at`, an `e` tag for each owned event id and appropriate `k` tags for their actual kinds. Publish to the configured relays that received the originals. Never delete another author's events or request private keys through the UI.
- Retain local hide, the root tombstone and linked cleanup if signing or publication fails; expose truthful failure and retry. Unpublished local-only items need no relay event. Capture retry metadata before original content disappears. No undo: a kind-5 request cannot be reliably recalled after publication.
- Relays may not honor deletion requests. Other clients may retain caches; independent media hosts are outside NIP-09. Deleting a root's own events does not delete other authors' replies or remove their readability locally.

## 6. Accessibility and acceptance checks

Preserve every existing `aria-label`, other `aria-*` attribute, role, tabindex, focus handler and live region verbatim. Add only the new controls, tombstone and dialog semantics. Do not rename `More, Dream by <name>` or `Reply options`, strip reply `tabIndex: -1` (`app/js/core.js:1093-1125`), alter inline heading focus (`app/js/core.js:616-638`), or replace the existing announcement/live-region infrastructure (`app/js/core.js`, `announce`, `AlertDialog` and modal focus manager; `#looscid-live`). No decorative emoji.

Test with keyboard and a screen reader: others have no Delete; own root/reply actions have the specified labels; opening or cancelling the dialog mutates nothing; Cancel/Escape return focus to the trigger; confirm runs once and announces the actual outcome. Root deletion displays `this Dream was deleted`, preserves readable replies across reload, and cleans linked alerts/subscriptions. Reply deletion preserves siblings, descendants and parent subscriptions. No undo is offered. Deleted content must not return from saved Dreams, replies, Liked, Redreams, edits, relay fetches or queued creation. Test local-only items, missing metadata, storage failures, signing refusal, offline relays and partial relay acceptance. Neither hide nor relay acceptance is guaranteed global erasure.

## 7. Remaining open questions for Carter

The root placeholder, retained replies, no undo, and cleanup of linked alerts/subscriptions are decided. Remaining implementation questions:

1. How should saved drafts lacking an explicit published-Dream link and older alerts lacking item-specific linkage be migrated or handled? Do not infer ownership/linkage from text or sweep unrelated records.
2. What metadata should the minimal tombstone retain to keep nested reply navigation usable without retaining deleted content? How should a separately deleted reply with surviving descendants be represented?
3. How should partial edit-event history and relay failures be presented, and how long should deletion retries be retained? Is independently hosted media deletion a separate supported action?
